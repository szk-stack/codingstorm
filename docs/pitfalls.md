# 踩过的坑：两个不报错的 bug

> 记录于 2026-09-17，Phase 1 开发期间。
> 这两个 bug 都不崩溃、不抛异常、不影响任务成功与否 —— 只是安静地给出错误结果。
> 写下来是因为它们代表的**思路陷阱**会重复出现。

---

## 先理解背景：数据层为什么长这样

要看懂后面的 bug，得先知道 `db.py` 的两个设计决定。

### 决定一：写操作在一个单独的线程里做

SQLite 的写入要落磁盘。如果直接在 asyncio 的事件循环里写，**整个服务会卡住** —— 事件循环是单线程的，它被阻塞时，所有 HTTP 请求、所有 WebSocket 推送都得排队等。

所以我们开了一个**专职写线程**：业务代码把要执行的 SQL 丢进一个队列，写线程从队列里取出来执行，结果再传回去。

```
事件循环线程                          写线程
    │                                  │
    │  把 SQL 丢进队列 ──────────────→ │  取出来执行
    │                                  │
    │  ←────────────── 结果传回来 ──── │
    │                                  │
  （期间事件循环继续处理别的请求）        │
```

### 决定二：写事件时「攒批提交」

一条简单的命令能产生几千个事件（实测有 2890 条 `thinking_tokens`）。如果每来一条就写一次磁盘，会非常慢。

所以 `append_events()` **只是把事件放进一个待写列表，不落盘**；写线程每隔一段时间（或攒够 100 条）才一次性提交：

```
append_events(A)  →  待写列表 = [A]
append_events(B)  →  待写列表 = [A, B]
append_events(C)  →  待写列表 = [A, B, C]
                     ...过一会儿...
                     一次性全部写入数据库 ← 这一步才真正落盘
```

**关键点：`append_events()` 返回时，数据还没有进数据库。**

记住这句话，bug 2 就是从这里来的。

## Bug 1：数据库连接被跨线程使用

### sqlite3 的一条硬规则

**一个连接在哪个线程创建的，就只能在那个线程里用。** 换线程用就报错：

```
sqlite3.ProgrammingError: SQLite objects created in a thread can only be
used in that same thread.
```

这是 sqlite3 的安全检查，防止两个线程同时用一个连接把内部状态搞乱。

### 我当时的想法

「既然连接不能跨线程，那我给**每个线程**配一个自己的连接不就行了？」

这是很常见的做法，Python 提供 `threading.local()` 专门干这个 —— 往里面存的东西，每个线程看到的是自己的一份：

```python
self._local = threading.local()

def _read_conn(self):
    conn = getattr(self._local, "conn", None)   # 这个线程的连接
    if conn is None:
        conn = self._make_conn(self.path)       # 没有就建一个
        self._local.conn = conn
    return conn
```

看起来天衣无缝。

### 问题出在哪

读数据的代码是这样的：

```python
async def query(self, sql, params):
    conn = self._read_conn()                                   # ①
    return await asyncio.to_thread(lambda: conn.execute(...))  # ②
```

**① 和 ② 不在同一个线程上。**

- 第 ① 行是普通 Python 代码，跑在**事件循环线程**上 → 连接在这里被创建
- 第 ② 行 `asyncio.to_thread` 的作用是「把这个阻塞函数丢到**线程池**里去跑」→ 连接在**另一个线程**里被使用

创建在 A 线程，使用在 B 线程。`threading.local` 费半天劲做的隔离**根本没被用上** —— 因为取连接和使用连接压根不是同一个线程，那个"每线程一份"的格子白设了。

### 怎么改的

既然连接注定要被别的线程碰，那就别再指望线程隔离了：

1. 建连接时明确关掉这个检查：`check_same_thread=False`（意思是"我知道我在跨线程用，我自己保证安全"）
2. 既然检查关了，安全就得自己保证 → **加一把锁**，同一时刻只允许一个线程碰它

```python
def _read(self, sql, params):
    with self._read_lock:                       # 排队，一次只进一个
        return self._read_conn().execute(sql, params).fetchall()
```

### 教训

`threading.local()` 这个工具本身没错，错的是**它隔离的对象和使用它的位置不在同一个线程**。用这类"和线程绑定"的工具时，得先确认：**创建和使用的代码，是不是真的在同一个线程上跑。**

## Bug 2：序号撞号，事件被静默覆盖

### 涉及的三个事实

**事实一**：`task_events` 表用 `(task_id, seq)` 作为主键。`seq` 是事件在任务内的序号：0、1、2、3……

**事实二**：插入语句是 `INSERT OR REPLACE`。意思是——**如果主键已经存在，就把旧的那条覆盖掉，不报错**。

**事实三**（前面背景里说的）：`append_events()` 只入队，不落盘。

### 我当时的写法

```python
async def _emit(self, task_id, etype, payload):
    seq = await self.store.next_event_seq(task_id)              # 查当前最大序号 +1
    await self.store.db.append_events([(task_id, seq, ...)])    # 入队（还没落盘！）
```

`next_event_seq` 执行的是：

```sql
SELECT COALESCE(MAX(seq), -1) + 1 FROM task_events WHERE task_id = ?
```

「查一下现在已经到几号了，下一个用它的下一个号。」

看起来也对：每发一个事件就查一次，怎么会重号？

### 为什么还是重号了

因为**查的时候，前面的事件还在队列里没进库**，所以每次都查到同一个旧值：

| 步骤 | 执行 `MAX(seq)+1` 时库里的实际内容 | 查到 | 分配的 seq | 待写列表 |
|---|---|---|---|---|
| 发事件 A | *(空)* | `-1` | **0** | `(0, A)` |
| 发事件 B | *(空 —— A 还在队列里没落盘)* | `-1` | **0** | `(0, A) (0, B)` |
| 发事件 C | *(空)* | `-1` | **0** | `(0, A) (0, B) (0, C)` |
| 写线程批量提交 | | | | A、B、C 主键都是 `(task, 0)` |
| | | | | **`INSERT OR REPLACE` → 只剩 C** |

**发出 5 个事件，数据库里只有 1 条。**

### 为什么完全没有报错

这是最要命的地方：

- `INSERT OR REPLACE` 遇到重复主键**是合法操作**，不会抛异常
- 事件丢了不影响任务本身 —— 文件照样创建成功，`result` 事件照样正常
- 接口返回 200，任务状态是 `awaiting_review`，一切看起来都正常

唯一的症状是：**查看执行记录时，事件条数比实际发生的少。** 你得去数才知道。

线上就是这么丢掉一整条 `Write` 调用的 —— 日志里明明有「写入 greet.py」，数据库里却找不到这个事件。

### 怎么改的

序号不要再去数据库查了，**在内存里自增**：

```python
if task_id not in self._seq:
    self._seq[task_id] = await self.store.next_event_seq(task_id)   # 只在任务开始时查一次
seq = self._seq[task_id]
self._seq[task_id] = seq + 1                                        # 之后全在内存里加
```

那个"只在开始时查一次"是有讲究的：进程重启后，内存计数器没了，得从数据库里已有的最大序号接着往下走，否则会从 0 重新开始，把历史事件覆盖掉。

### 教训

`append_events()` 这个函数名叫「追加事件」，读起来像是"存进去了"。但它实际是**入队**。

**一个"暂存"环节横在中间时，任何"先读当前状态、再决定写什么"的逻辑都会失效** —— 因为你读到的不是最新状态，是**上一次真正落盘时的状态**。

遇到这类"读-改-写"的操作，要么保证读和写在同一个原子单元里，要么就把计数器放在内存里自己维护。

## 为什么单元测试没抓到

**Bug 1** 是抓到了的 —— 测试一跑就报错，因为它是硬失败。这属于运气好。

**Bug 2 单元测试永远抓不到**，因为：

- 单测里每发一个事件就 `flush_events()` 刷一次盘，序号永远是对的
- 撞号只在「**连续发多个事件、中间不刷盘**」时发生 —— 而那正是线上真实运行的节奏

它是在执行机上跑端到端、**肉眼数事件条数**才暴露的。

### 一句话总结这一类 bug

**逻辑错、边界错、假设错，都不会报错；只有"跨越了一层抽象但以为对面还守规则"才会又错又安静。**

- Bug 1 跨的是**线程边界**：以为 `threading.local` 隔离了，但取值和用值不在一个线程
- Bug 2 跨的是**入队与落盘的边界**：以为写进队列就是写进数据库了

以后再遇到「加了异步/加了一层缓冲/加了一个后台线程」之后行为诡异但一切正常的情况，先想想是不是这两类。
